# Full audit in the emulated VR environment — 2026-09-09

All 82 campaign modules swept **inside a presenting immersive session**
(`npm run vr:sweep -- --vr`), then every major root cause the sweep named taken
to a settled cause and fixed, then re-swept under the same conditions.

## What this settles, and what it does not

The sweep warps into each module, runs a fixed battery, records what is wrong and
moves on whether the module passed or not. It answers a narrow question: of
everything the engine must load, build and render to make a module playable at
all, what is broken?

It does not play the game. It cannot say a quest is unfinishable, that combat
maths are wrong, or that a conversation dead-ends — those need the playthrough
driver. And it is **not device evidence**: IWER renders through an ordinary page
WebGL context, so comfort, compositor cadence and reprojection are all outside
what it can see. Those still need the headset.

New this run: `--vr`, so every module was measured through the VR frame path
rather than flatscreen. All 82 records carry `presenting: true` — the sweep's own
guard against reporting flatscreen results as VR evidence.

**The VR frame path introduced no defect class of its own.** Every finding below
also occurs in flatscreen, and the pre-fix totals sit inside the measured
run-to-run noise band of the flatscreen baseline (spread 8 clean modules / 18
findings over five identical runs). At module load, build and render level, VR
costs nothing in correctness.

## Root causes fixed

Each was taken to a settled cause before anything was changed. Where the answer
was retail data rather than an engine fault, that is stated with the evidence
that settled it — a finding may be closed on evidence, never on assumption.

### 1. Every merchant in the game was empty — 12 modules

`ModuleStore.load()` guarded on `getResRef()` and then looked the UTM up with
`getTemplateResRef()`. A GIT's StoreList struct names the blueprint `ResRef`;
every *other* object type names it `TemplateResRef`. The store is the one type
where those differ, and the method used one for the guard and the other for the
lookup, so `loadCachedResource` was always handed null.

Nothing degraded visibly, which is why it survived: inventory, markUp/markDown,
onOpenStore and locName all silently kept their constructor defaults.

**What settled it.** All 12 modules containing a store report the failure and no
module without one does — 12/12, no false positives in the other 70.
`ForgeStore`, the project's own GIT reader and writer, moves this field through
`ResRef` in both directions.

`dcf00ff3`. The recovered reference is also written back to `templateResRef`,
which `save()` serialises and nothing else on a GIT-loaded store populated — so
the blueprint was being lost from the savegame too.

### 2. A fragment shader that could not compile — 6 to 9 modules

`USE_NORMALMAP` and `TANGENTSPACE_NORMALMAP`/`OBJECTSPACE_NORMALMAP` guard
opposite halves of the same code in three's chunks: the first *declares*
`uniform sampler2D normalMap`, the others *sample* it. The water branch of
`applyTXIToMaterial` deleted `USE_NORMALMAP` alone and left
`TANGENTSPACE_NORMALMAP` set from the NORMAL-bumpmap branch above it.

Any texture that is both a NORMAL-type bumpmap and carries `waterAlpha` then
failed outright — `'normalMap' : undeclared identifier`. The material does not
degrade in that case; it never builds.

`dc7f07b1`, clearing the group through one helper that states the invariant, plus
a test that scans for any future site dropping `USE_NORMALMAP` on its own — which
is exactly how this arrived.

### 3. Dialogue animations used a numbering the engine did not read — 4 modules + 3 variants

Two numbering schemes reach `animationConstantToAnimation` and only one was
handled. The named constants are the engine's own: `PAUSE` is 10000 and resolves
to row 6 (`pause1`), `SCANNING` is 10412 and resolves to row 471 (`scanning`).
Dialogue and script data also carry a second form — the animations.2da row index
plus 10000 — and those matched no case at all, so the creature reported
"Animation Missing", froze to PAUSE, and the authored animation never played.

**What settled it.** Three sightings in one sweep, each of which reads correctly
only under the row reading:

| constant | row | row name | seen on |
|---|---|---|---|
| 10074 | 74 | `horror` | Tame Boma, Tame Cannok, Starving Tuk'ata — beasts hit by Force Horror |
| 10459 | 459 | `forcecrush` | Sith Drexl Trainer |
| 10471 | 471 | `scanning` | a droid NPC |

The last is the cross-check: the switch independently maps `SCANNING` to that
same row 471, so two unrelated paths agree on what row 471 is.

`71433c98`. The fallback is deliberately **restricted to constants that are not
`ModuleCreatureAnimState` members**, because for a named constant the row reading
is actively wrong — `PARRY` is 10012 and row 12 is `pausesh`. An unrestricted
fallback would replace a missing animation with a visibly wrong one.

Row indices were read from the live 2DA with `tools/vr-emulator/probe-animations.js`
rather than guessed.

### 4. Camera framing did not survive a save — all cameras

`ModuleCamera.save()` wrote three float properties as integer types:
`FieldOfView` as DWORD, `Height` as BYTE, `Pitch` as BYTE. None can hold what a
camera carries — a fractional FOV, a negative height, a negative pitch.
`GFFField.setValue` reports the violation and stores the value anyway, so the bad
value reached serialization and wrapped: the same -1/255 confusion that silently
disabled every item property after a save/load.

The sweep caught one instance (`BYTE OutOfBounds label='Height' value=-1.5` in
503OND), but the fault is per-camera, not per-module. That matters more here than
upstream, since cutscenes are reprojected onto a theater screen.

`ForgeCamera` reads and writes all three as FLOAT in both directions, which
settles the authored types. `d81f10cb`.

### 5. A rejected movie queue stopped every later module load — surfaced by the re-sweep

`VideoManager.playMovieQueue` rejects when a queue is already active. In
`LoadModule` that call was neither awaited nor caught, so the rejection escaped
as an unhandled page exception and the completion callback never ran.

That callback is the whole post-load setup — spawn scripts, the in-game overlay,
the scene compile — and `loadingModule = false` on its last line. Leaving that
flag latched makes `LoadModule` return immediately from then on, so **every later
transition is a silent no-op**. The failure is a hard stop at the next door, not
a dropped movie.

The boot-path call to `playMovieQueue` already recovers exactly this way; this
one did not. `549fb479` names the completion and runs it on the rejection path
too.

Caught once in 82 modules, and it did not reproduce on a targeted re-run of the
same 204TEL → 205TEL transition — which is what a timing-dependent race looks
like, and why the recovery matters more than the trigger. Nothing in the six
earlier fixes touches `VideoManager` or the movie path; the likeliest reading is
that the quieter, faster load this pass produced shifted the timing enough to
reach a window that was always there.

The next full pass confirmed both halves of that reading: the race fired again,
in **605DAN** rather than 205TEL, and this time it appears as a logged recovery
instead of an unhandled exception. It recurs at roughly one module in 82 and is
not tied to a particular module.

One caveat on severity. The sweep's probe sets `GS.loadingModule = false` before
every module precisely so one bad module cannot silence the rest of the run, so
the sweep **could never have shown the cascading consequence** — it would have
reported one noisy module and 81 healthy ones. Real play has no such reset. The
observed blast radius understates this defect rather than overstating it.

**The trigger, fixed separately in `d576fbda`.** Movie-mode ownership is taken in
`playMovieQueue` and released in exactly one place — `playNextMovie`, when the
queue drains. Nothing released it when a queue was *abandoned* instead, and a
module transition abandons one every time it happens mid-movie. `UnloadModule`
already resets the audio engine, lights, wind, cursor and module objects; the
VideoManager was the one manager left out.

The leaked flag was only the visible half. `LoadModule` pushes the incoming
module's movies onto the same static queue a few lines after calling
`UnloadModule`, so an outgoing queue still draining would have swallowed them and
played them as part of the outgoing module — and the outgoing `onQueueComplete`,
the previous load's completion, was still armed to fire against the new module.

`VideoManager.reset()` abandons all four pieces together: the queued movies, the
arming completion, the decoder, and the ownership flag. It also covers quitting
to the main menu, which reaches `UnloadModule` from `MenuOptions`.

Evidence across three full passes: the race fired once in each of the two runs
before the trigger fix — 205TEL in one, 605DAN in the other — and **zero times**
in the run after it. The recovery stays in place regardless: it is what makes the
failure non-fatal if the race is ever reachable by another path.

### 6. A saber node with no diffuse map failed to compile at all — 3 modules

Surfaced only once the normal-map failures stopped masking it.
`sampledDiffuseColor` and `map` are declared only inside the `USE_MAP` block, and
`USE_MAP` is set only when the map uniform has a value. The `SABER` branch used
both without that guard, while `SABER` is set from the model's node type alone —
`(nodeType & Saber)` — with no reference to whether a diffuse map resolved.

A saber node whose texture is absent, or has not resolved yet, compiled a
fragment shader referencing two undeclared identifiers, so the whole material
failed to build rather than merely losing its blade texture. Same shape as the
normal-map defect: a define group half-set. `9660b3e2`.

Verified twice: a targeted re-sweep of the three modules left 504OND and 506OND
clean and 907MAL carrying only its known `sion` dialogue finding, and the final
full pass reports **zero** shader findings across all 82 modules.

## Closed on evidence rather than code

The engine reported several *absent but optional* retail assets at error level.
In each case it already degrades correctly and carries on; the cost was the
report, and error volume is what buries the reports that do mean something. Every
absence was verified against the install before being reclassified.

### Lip-sync — 15 to 25 modules per run, the top root cause by module count

The largest console-error signature in the sweep, and not a fault. The install
ships 77 lip archives for 82 modules, and plenty of voiced lines carry no `.lip`
even inside a module that has one — `303303han001` and its siblings are absent
from every archive here. `LIPObject.Load` already resolved `undefined`,
`setLIP(undefined)` is a valid state, and every consumer guards on
`instanceof LIPObject`, so the line simply plays unlipped.

`3cf6ddb4` carries the distinction on a typed `ResourceNotFoundError` rather than
on a message match, so any caller can tell "never shipped" from "there and will
not read". A lip that exists and fails to read is still an error.

One case is worth recording because it looked like a lookup bug and is not:
`221carthend057` *does* exist, in `lips/205TEL_loc.mod` and `lips/221TEL_loc.mod`,
with its VO at `StreamVoice/221/carthend/`. It is requested while in 207TEL,
whose own lip archive does not contain it and neither does the global
`lips/localization.mod`. Both archives are correctly registered — the reference
simply crosses modules in the authored data.

### Ambient audio and stream music — 2 modules

905MAL's area asks for `streammusic/bed_905mal.wav`; this install ships 901
through 904 and 906, and no 905. 106PER's emitter asks for `amb_compb_06`; the
install ships 01 through 05.

`bd4eb3be`. Two problems in one line: the report also logged the whole 2DA row,
so it read "Ambient Audio not found **Object**" and identified nothing. It now
names the resref and reports at warn level.

### A door model TSL does not ship — 3 modules

`genericdoors.2da` names `t_door01`. That resref appears **nowhere** in the
install — not in `chitin.key`, not in any module archive, not in `override/`. The
engine's report is accurate and its degrade is correct; the door ends up
invisible while still solid and interactable.

Left as an error, because unlike a missing lip this one is visible in play, and
in VR an invisible-but-solid door is worse than it is on a monitor. It is a
**data** fix, not an engine fix — the shape this project has already committed to
for level geometry, so it survives an engine switch.

## What the sweep cannot see, and one thing found by looking instead

The sweep counts what the engine *reports*: console errors, load failures,
unresolved templates. It renders 30 frames per module and never looks at them. A
model that loads correctly and is drawn in the wrong place produces no error at
all, so **composition is entirely outside what any of this measures** — a blind
spot worth stating as plainly as the comfort and cadence ones.

An example surfaced during this pass, by attaching read-only to the running
sweep and measuring the scene around the camera rather than reading the log:

**The player's own character model is rendered in front of the VR camera in every
module.** Five consecutive samples in a settled 304NAR, all identical: 15 of 15
meshes of `p_t3m4` drawn, all 15 in front of the camera in camera space, 11 of
them inside the view frustum, nearest part 1.16 m from the eye. In a settled
301NAR the avatar is effectively visible at 1.61 m with every ancestor visible.

DESIGN.md commits to first person and the rig is welded to the avatar, but there
is no avatar-suppression logic anywhere in `src/vr/`. This is unimplemented
rather than regressed, and it is why it appears in every module: the player is
always there.

Two suspects ruled out on the way, recorded so they are not chased again: the 11
`PointLightHelper` spheres are real but their `light_helpers` group is
`visible: false`, and the video planes are neither visible nor parented. Note
that per-object `visible` is misleading here — three's `traverse` descends into
hidden parents, so effective visibility has to be computed up the ancestor chain.

**Fixed in `028410d1`.** `hidePlayerBodyForFirstPerson` hides the controlled
character's model for the first-person world submission and restores it in a
`finally`, so a throwing render cannot leave the player invisible to every other
camera. Authored cutscenes reproject a shot while the player stands in the real
room, so the body belongs in that render; the prerendered-movie path already
hides the whole world behind its screen; the flatscreen camera and party-select
portraits are untouched. It follows `hideWorldForTheater` exactly, including its
rule that only an already-visible object is touched, so the restore can never
turn on something the engine deliberately hid.

Visibility rather than layers because `renderer.shadowMap.enabled` is never set
in this engine — nothing casts shadows, so there is nothing for layers to
preserve. That is the decision to revisit if shadows are ever enabled: the
avatar would stop casting one in first person.

Verified live rather than by inspection, and deliberately *at render time* —
reading `model.visible` from outside the frame always shows it visible, because
the hide lasts exactly one render call. Sampling inside `renderer.render` across
453 calls: **0 of 151 first-person submissions drew the body, and 302 of 302
other renders still did.** Scoped precisely to the eye view, with nothing else
losing the avatar.
