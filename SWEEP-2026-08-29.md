## A. Correctness

### A1 — A mod-layer `.mdl` can be paired with the retail `.mdx` — FIXED 2026-08-29

This is the one that matters most for the model-upgrade half of the work in
progress.

`ResourceLoader.setOverrideResource` picks the winning layer per
`(resourceType, resref)` **independently**. `MDLLoader` then resolves the two
halves of a model as two unrelated lookups:

```ts
const mdlPromise = ResourceLoader.loadResource(resMDL, resref);
const mdxPromise = ResourceLoader.loadResource(resMDX, resref);
const [mdl_buffer, mdx_buffer] = await Promise.all([mdlPromise, mdxPromise]);
const model = OdysseyModel.FromBuffers(mdl_buffer, mdx_buffer);
```

A mod layer that ships `foo.mdl` but not `foo.mdx` — a real packaging
mistake, and also what happens if one of the two files is filtered out by
casing, extension, or an archive that flattened differently — hands
`FromBuffers` a mod MDL describing vertex offsets into a retail MDX. The MDX
is raw vertex data addressed by offsets the MDL states. A mismatched pair is
not a clean failure: it is garbage geometry, or a read past the end of the
buffer.

The diff already recognises this hazard for textures and solves it there —
`.txi` is only used when `txiCandidate.layerOrder === candidate.layerOrder`.
The MDL/MDX pair has the identical hazard and no equivalent guard.

**Fix.** Resolve model pairs as a unit: pick the highest layer that supplies
*both* `.mdl` and `.mdx` for that resref, and fall through to the next layer
down if either is missing. Generalise the same rule the texture path already
uses rather than writing a second one — a small
`resolveCompanionEntries(resref, [primaryType, requiredCompanionType])` on
`ResourceLoader` covers `mdl`/`mdx` and `tga`/`txi` both.

Worth a log line when a layer is skipped for an incomplete pair. Silently
falling back to retail is correct behaviour but reads to the player as "my
mod didn't install".

**Fixed as described, with fall-through chosen over hard-fail (Allen,
2026-08-29).** What landed:

- `OverrideResources` now keeps *every* layer offering a resource, highest
  first, instead of only the winner. The old map discarded losing layers at
  registration time, so there was nothing to fall through *to* — this was a
  prerequisite, not a refactor.
- `ResourceLoader.selectOverrideLayer(resRef, primaryTypes, required, optional)`
  walks layers highest-first and returns the first that can supply a complete
  resource. `primaryTypes` is a within-layer priority order, which is how
  `.tpc` beats `.tga` inside a layer without a low-layer `.tpc` beating a
  high-layer `.tga`.
- `loadModelPair` uses it with `[mdl]` required-companion `[mdx]`. When no
  layer has both it resolves *both* halves from the archives via a new
  `loadArchivedResource` — going back through `loadResource` for either half
  would have reintroduced the mismatch. A read failure mid-pair is treated the
  same as a missing file: the whole layer is dropped, not half of it.
- The `.tga`/`.txi` path collapsed onto the same helper, replacing its bespoke
  `layerOrder` comparison.
- `MDLLoader` and Forge's `fetchModelBuffers` (same defect, same shape) both
  route through it.
- Skipped layers warn once per `layerId:resref`, naming the missing companion.

Gates: engine typecheck clean; 115 suites / 1008 tests green (8 new); all five
webpack bundles compile. Forge's typecheck has 56 pre-existing errors, count
unchanged and none in the touched file.

### A2 — Dynamic lights are culled against a frustum at the world origin in VR — FIXED 2026-08-29

`GameState.updateViewportFrustum()` is called mid-frame in `UpdateIngame`
(GameState.ts:3087), and `GameState.lightManager.update()` runs four lines
later. `LightManager.canShowLight()` culls every light with
`light.isOnScreen(this.context.viewportFrustum)`.

While a WebXR session is presenting, three writes the reference-space-LOCAL
head pose into its XR camera at frame start and only composes the rig during
`render()`. So the frustum built at line 3087 sits near the world origin —
exactly the defect fixed for doors and creatures in c0d1a690, which moved the
rebuild to *after* `GameState.Render` for that reason. This instance was not
moved.

Consequence: area lighting is culled against a viewpoint that is not the
player's. Lights extinguish and re-ignite as the world origin swings through
that phantom frustum. The comment at GameState.ts:3000 already documents the
mechanism; the code four hundred lines earlier still has the bug.

`UpdateDialog` (3123), `UpdateMinigame` (3143) and `UpdateFreeLook` (3179)
carry the same call in the same position.

Room culling in `ModuleArea` (ModuleArea.ts:812) is *not* affected — it runs
inside `module.tick()`, before the clobber, so it reads the correct frustum
left by the previous frame's post-render rebuild.

**Fix.** Delete the mid-frame `updateViewportFrustum()` from all four update
paths. The post-render rebuild in `Update` already leaves a correct frustum
for the next frame in both flatscreen and XR. Removes a bug and a redundant
matrix multiply per frame.

**Fixed as described, on top of D's extraction.** There is now exactly one
rebuild in the frame. What this trades: flatscreen light and reticle culling
takes one frame of latency, because those two were the only consumers that
read the mid-simulation rebuild. Room and selectable-object culling are
unaffected — both run inside `module.tick()`, ahead of where that rebuild
sat, so they always read the previous frame's frustum anyway.

`src/tests/viewport-frustum-xr-pose.test.ts` had a test asserting the
mid-simulation call *must stay* "for the flatscreen path". That premise is
what this overturns, so the test was replaced rather than deleted: it now
pins exactly one call site, that it follows `Render`, and that all four modes
route through the shared helper. Its header records why the first fix left the
second instance behind. (The sibling test that broke was brittle for an
unrelated reason — it searched a fixed 900-character window after `Render`,
which my added comment pushed the call out of.)

### A3 — Override precedence now prefers `.tpc` over `.tga` in the retail layer too

**DEFERRED 2026-08-29 by Allen** — revisit once the layered mod
texture/model work is finished, not before. Recorded here so it is not
rediscovered as a surprise; do not act on it yet.

`TextureResolver.resolveExact` reorders its sources to
`['override-tpc', 'override-tga']`, and `getOverrideTextureCandidate` breaks a
same-layer tie in favour of `.tpc`.

For a mod layer this is right, and the README documents why (UCO Redux ships
a compressed TPC variant). Applying it to the retail `Override` directory as
well is a behaviour change: retail Odyssey resolves a loose `.tga` in
`Override` ahead of a `.tpc` of the same name, and that is the classic KOTOR
texture-replacement route. Any retail-era mod already installed into
`Override` as a bare `.tga` now silently loses to a `.tpc` sibling.

**Fix.** Keep highest-layer-wins across layers; inside the `retail` layer,
restore `.tga` before `.tpc`. That preserves the new feature and retail
compatibility at once. If `.tpc`-first is deliberate for retail as well, record
that in the code, not only the README — it is a decision, not an
implementation detail.

### A4 — `searchOverrideEntry` is typed `Promise<Uint8Array>` and returns `undefined`

`ResourceLoader.ts`. Two paths return `undefined` (empty buffer, read

A symptom, not the disease — see C1.

### A5 — The `X-Kotor2VR-Asset-Layer` header has no reader

`asset-service.js` sets it on every `/assets/` response.
`HttpGameFileSystemBackend` learns the layer only from the *directory listing*
(`entry.layer`), never from the file response. The header is currently
unverified and unused. Either wire it into `readFile` — so a file fetched

per-file-pair check for A1 would want — or drop it.

## B. Performance

Ordered by expected win. All independent.

### B1 — `logarithmicDepthBuffer: true` disables early-Z

`GameState.ts:1631`. Logarithmic depth writes `gl_FragDepth` in every fragment
shader, which defeats early depth rejection on essentially every GPU and is
disproportionately expensive on the tile-based GPU in a Quest. Cameras are
built with a 0.01–15000 range; a near plane raised to ~0.05 — a headset never
presents anything closer than a few centimetres anyway — makes ordinary depth
sufficient across that range.

One flag, A/B-able on the existing XR benchmark, and plausibly the largest
single fill-rate win available today. Measure before believing it.

**Made measurable 2026-08-29; default deliberately unchanged.** The whole
content of this item is "measure it", and I cannot — it needs the headset. So
what landed is the A/B, not a flip: `parseRendererDepthMode` reads `?depth=`
from the launch URL, the renderer is built from it, and startup logs which
mode it got. A normal launch is the control arm and behaves exactly as before.

Booked as **H7/H8** in HEADSET-TEST-PLAN.md, deliberately as a pair: H7 is the
frame-time delta, H8 is whether linear depth z-fights on long corridors and
large floors. H7 without H8 is not a result — a faster frame that z-fights is
not a win.

Two things worth knowing that came out of reading three r149's implementation.
`USE_LOGDEPTHBUF` is defined whenever the flag is on, but the per-fragment
`gl_FragDepthEXT` write is gated on `EXT_frag_depth` being present. So the flag
has two failure modes, not one: with the extension it is correct and costs
early-Z; without it, three interpolates depth across the triangle instead,
which is visibly wrong on precisely the large wall and floor triangles Odyssey
rooms are made of. Both branches argue for trying without it. Also, the VR
camera already runs `near = 0.05` — the near-plane half of the original
suggestion is moot.

### B2 — `TextureLoader.LoadQueue` drains the whole queue in one unbounded `Promise.all` — REVERTED 2026-08-30

`TextureLoader.ts:468`. Every queued texture starts at once, and TPC/DXT
decode is synchronous main-thread work. `GameState.Update` will not start a
second drain until the first resolves, so a module load is one long stall
rather than a spread cost. In VR a stall that size drops the compositor to
reprojection and the player feels it directly.

This gets worse, not better, with mod texture packs: UCO Redux-class packs
replace character, creature, droid and equipment textures with substantially
larger ones, so the same queue now decodes several times the bytes.

**Fix.** Cap concurrency and give the drain a per-frame time budget — resolve
until ~4 ms of the frame is spent, yield, continue next frame. The queue is
already a plain array; the change is contained.

**Fixed 2026-08-29 — but narrower than the item first implied.** `LoadQueue`
has ~45 call sites, and most are behind a loading screen and legitimately need
every texture before continuing. Making *all* of them budgeted would have made
loading slower for no gain. So there are now two entry points:

- `LoadQueue` — exhaustive, unchanged contract, for callers behind a loading
  screen.
- `LoadQueueWithinBudget(ms)` — resolves until the budget is spent and returns
  whether the queue emptied. Only `GameState.Update`'s gameplay drain uses it,
  which is the one that stalls live frames.

Both share a bounded worker pool (`MAX_CONCURRENT_TEXTURE_LOADS = 8`) in place
of the unbounded `Promise.all`. That does not reduce total CPU — decode is
synchronous either way — but it bounds live decoded buffers and stops a module
load opening several hundred concurrent reads at once.

One subtlety the budgeted path had to handle that the exhaustive one does not:
`LoadQueue` swaps the whole `pendingSubscribers` map out at the start. A
partial drain cannot, or it would drop the subscribers of every request it did
not reach — so it releases entries per-request instead. There is a test for
exactly that.

`FRAME_TEXTURE_BUDGET_MS = 4` is provisional and openly a guess: a 72 Hz frame
is 13.9 ms total, and the right value is whatever keeps the headset off
reprojection while still clearing the queue promptly. Tune it against H3.

---

**REVERTED IN FULL, 2026-08-30, at Allen's call.** Loading screens came up flat
green during manual testing. `LoadQueue` is byte-identical to HEAD again and
`GameState.Update` is back on the exhaustive drain; `LoadQueueWithinBudget`,
the concurrency cap and their tests are gone.

**The revert is not a diagnosis.** B2 was the newest change touching startup
texture *timing*, which made it the best suspect, but it was never confirmed as
the cause — the green persisted through an earlier fix to it, and no
reproduction was ever obtained outside manual testing. If the green survives
this revert, B2 is exonerated and the cause lies elsewhere; that outcome is
worth recording either way.

**What the green means**, established while diagnosing and worth keeping:
`GameMenu` draws a background-void sprite at z=-6 tinted RGB(0.102, 0.698,
0.549) — that exact green-teal — behind a `transparent` background material at
z=-5. A flat green screen is therefore never a shader fault or a wrong clear
colour. It means a background texture never reached its material, and the void
is all that remains to draw. That narrows any future instance to texture
delivery immediately.

**A real bug found inside B2 before the revert**, worth knowing if it is ever
re-landed: the budgeted drain read `pendingSubscribers` *after* an `await`.
`LoadQueue` assigns `pendingSubscribers = new Map()`, and it is called from
menus, GUI controls and module load — so if that landed mid-batch, every
subscriber beyond the primary silently lost its update. The texture resolved
and the other materials that had asked for it stayed blank. A re-land must
claim the batch's subscribers synchronously, before the first await.

**Kept from the episode:** `GameState.Update`'s drain now has a `.catch` before
its `.then`. The latch was `LoadQueue().then(() => loadingTextures = false)`,
so a single rejection left it stuck on `true` and nothing resolved another
texture for the rest of the session — a permanently untextured world presenting
as no error at all. That fault predates B2 and outlives its revert.

### B3 — Animated (`procedureType == 1`) TPCs are DXT-decompressed and re-compressed in JavaScript — FIXED 2026-08-30

`TPCObject.ts:234-256`. Per mipmap: `dxtJs.decompress` each frame → stitch
onto an `OffscreenCanvas` → `getImageData` (a synchronous GPU readback) →
`dxtJs.compress` the merged image. A JavaScript DXT *encoder*, on the main
thread, per animated texture, per mipmap level.

Nothing requires the recompress. Either stitch the frames in DXT block space
(4×4 blocks; verify frame dimensions are multiples of 4 in the retail set) or
upload the merged RGBA as an uncompressed texture and skip both the canvas
round-trip and the encoder. Either removes the encoder entirely.

**Fixed 2026-08-30 by block-space stitching.** DXT stores independent 4×4
blocks in row-major order, so the atlas is a block-grid copy: each frame's
block row moves into the destination unchanged. Decoder, encoder, canvas and
readback all gone.

Measured on a representative animated texture — 512×512 atlas, 4×4 grid of
128×128 frames, DXT5, full mip chain:

| Route | Time |
|---|---|
| Old, decode + encode only (canvas readback **excluded**) | 49.4 ms |
| New, block copy | 0.45 ms |

~110×, and the old figure is an undercount because it omits the
`putImageData`/`getImageData` round-trip. Per animated texture, on the main
thread, during load.

It is also **lossless**, which the old route was not: re-encoding re-quantised
every animated texture through a second lossy DXT pass. Animated textures
should now look slightly better, not merely load faster.

Three things worth recording:

- The pixel-space route is kept for the tail mipmap levels, where a frame
  shrinks below one 4×4 block and the block grid stops describing the image.
  Those levels are tiny; the expensive ones are all block-aligned.
- `TPCObject.canvas` turns out to be write-only — its one reader is commented
  out — so the per-level `OffscreenCanvas` retained per animated texture is
  gone too. That is a memory win on top of the time.
- Correctness is pinned by decoding: the test stitches synthetic frames, then
  checks the atlas decodes — through the real `dxt-js` decoder — to exactly
  the pixels each frame decodes to alone. Block arithmetic that is off by a
  row still yields a valid-looking image, so byte-length and shape assertions
  would not have caught it.

**Found while doing this, not fixed.** For an *uncompressed* animated TPC the
existing code calls `dxtJs.decompress` on data that is already RGBA, then
re-encodes it, while `dds.format` says `RGBAFormat`. That looks broken on its
face. I left it alone: the new path is gated on `header.compressed`, so those
textures take exactly the route they took before. Probably no retail animated
texture is uncompressed, which would explain why it has never shown — but that
is a guess, and confirming it needs the module sweep (C2), not a code reading.

### B4 — The VR panel re-renders the whole legacy GUI scene every XR frame — FIXED 2026-08-30

`VRPanelHost.renderGuiLayers`, called from `VRSpike.renderPanel` and
`renderInGameOverlay` on every frame a panel is open, clears and re-renders
the GUI scene into a render target up to 1536×1536 — and toggles
`renderer.xr.enabled` off and on around the pass, forcing three to rebuild
its render state twice per frame.

A KOTOR menu changes only on input or on an authored animation. Add a dirty
flag: repaint on pointer/input events, on menu content change, and on a
low-rate heartbeat (~15 Hz) for animated content; otherwise reuse the
texture. At 72 Hz with a panel open that removes on the order of 55 full GUI
passes per second.

**Fixed 2026-08-30.** `VRPanelRepaintPolicy` gates the composite;
`VRPanelHost.renderGuiIfChanged` applies it. Measured in test: 9 composites
per second where there were 72, an 87% reduction on a static panel.

**Two corrections to what this item claimed.**

*First, the value is smaller than "55 wasted passes per second" implies.*
`renderPanel` only composites while a menu is the foreground menu, and
`INGAME_OVERLAY_PANEL_ENABLED` is false, so during ordinary gameplay — the
H3 perf window, the case that actually matters — this pass does not run at
all. The win is confined to time spent with a panel open: inventory, journal,
map, equipment, options. Real, but not on the critical path.

*Second, "toggles `renderer.xr.enabled` off and on, forcing three to rebuild
its render state twice per frame" was wrong.* `xr.enabled` is a plain boolean
property; `WebGLRenderer.render` only reads it to decide whether to substitute
the stereo cameras. Toggling it costs nothing. The cost is the clear and the
scene render, which is what got gated.

**The design, and what it deliberately cannot see.** A blanket dirty flag
would have frozen the main menu's rotating model and all of character
creation, which repaint their own textures every engine frame with no input.
So the gate keys off a `GuiSurfaceRevision` counter bumped inside
`renderGuiSceneToTexture` — the single chokepoint every GUI-owned offscreen
render already passes through. Marking the chokepoint rather than each control
means `LBL_3DView`, `GUIListBox`, and any future animated control are covered
without an opt-in anyone can forget. It also gets list-content changes free,
since a list box rebuilds its texture when its contents change.

What the gate genuinely cannot observe is a menu mutating its own controls
with no offscreen repaint, no pointer movement and no input — a timer-driven
text field, a health bar on the equipment screen. Nothing cheap detects that
short of a revision counter threaded through all 2772 lines of `GUIControl`.
Hence the 100 ms floor, which bounds how long such a change can go unseen.
That is a real, if small, correctness cost knowingly taken for the reduction;
100 ms of staleness on a health bar is imperceptible, and the floor is the
only thing standing behind it.

The policy lives inside `VRPanelHost` rather than in `VRSpike`. The render
target keeps its pixels while hidden, so a policy that outlived a `clear()`
would show a reopened panel the last frame of the previous one — and there are
five `clear()` sites to remember. Owning it in the host makes that
unforgettable rather than merely documented.

`renderGui`/`renderGuiLayers` stay ungated: the cutscene theater path drives
them directly and its content changes every frame by definition.

### B5 — The renderer is pinned to WebGL 1 — ATTEMPTED AND REVERTED 2026-08-30

`GameState.ts:1625` creates the context explicitly as `getContext('webgl')`
and hands it to `WebGLRenderer`. three uses the supplied context, so
`capabilities.isWebGL2` is false engine-wide.

WebGL 2 costs one line here and buys instancing without an extension, integer
textures, and `texStorage` (fewer driver re-validations on upload — which
matters more once mod packs enlarge every upload). It is also the
precondition for any multiview path at all.

Risk: the engine's shaders are authored against GLSL ES 1.00. three's WebGL2
path still compiles those, but the material/shader layer needs a pass. Its
own task, with a flatscreen A/B before it goes anywhere near VR.

**Done, and this one is verified against the real build rather than by
argument.** WebGL 2 is the default; `?gl=webgl1` is the escape hatch, and the
engine falls back on its own if the browser cannot supply WebGL 2.

The shader question could not be settled by reading. three r149 sets
`rendererExtensionFragDepth = isWebGL2 || extensions.has('EXT_frag_depth')`, so
under WebGL 2 the logarithmic-depth chunk still emits `gl_FragDepthEXT` into a
GLSL ES 1.00 shader — legal or not depending on how the browser translates
ESSL1 in a WebGL 2 context. Since logarithmic depth is the default path, a
wrong answer there would break everything. So it was run instead of reasoned
about: `npm run vr:check`, the full browser build under an emulated Quest 3,
**24/24 pass** with `pageErrors=0`, `console-errors-baseline errors=4` (against
a ≤60 budget), `texture-resolution-baseline distinctFailing=14` — unchanged
from the WebGL 1 baseline — all six GUI-pack textures resolving, and 90 XR
frames delivered.

**That first run proved less than it appeared to.** `vr-check-metrics.json`
stores aggregates, not console lines, so nothing in it distinguished a WebGL 2
run from one that had silently fallen back — which is the exact failure mode
this change introduces. The harness now reads `rendererContextMode`,
`capabilities.isWebGL2`, the depth mode and `capabilities.logarithmicDepthBuffer`
off the live renderer, and `renderer-context-is-webgl2` asserts both halves:
what the engine believes it asked for, and what three actually observed. A
silent fallback now fails the gate instead of passing it quietly.

Nothing else in engine code assumed WebGL 1 — no `getExtension` calls or
extension-gated branches outside the Forge app.

---

**REVERTED. WebGL 2 does not render this engine.** Allen hit flat-green startup
screens in manual testing. Captured from the same build at the same moment,
with the same two mod layers loaded, differing only in context version:

| Context | Result |
|---|---|
| `?gl=webgl1` | LucasArts legal screen renders correctly |
| `?gl=webgl2` | solid green, nothing else |

Captured to `tools/vr-emulator/evidence/greenscreen-webgl{1,2}.png` — that
directory is gitignored, so regenerate them with
`node tools/vr-emulator/probe-greenscreen.js --url <launch>`. The default is
`webgl1` again; the option stays so this can be investigated without
re-plumbing anything.

**Why every check missed it.** Three things compounded:

1. `vr:check` asserts *behaviour and resolution*, not pixels. It passed 25/25
   under WebGL 2 — engine boots, save loads, 90 XR frames delivered, texture
   baseline unchanged, no page exceptions — while the screen was green. A gate
   that never looks at the image cannot see a rendering fault.
2. There were no shader-compile errors and nothing thrown, so the console
   budget check stayed green too. The failure is silent.
3. Every run I made started the asset service with **no `--mod` roots**, while
   Allen runs two. That turned out not to be the cause, but it meant my
   "verified" configuration was not his.

**What is and is not implicated.** Not the loader: under WebGL 2 the Override
index still builds correctly across mod layers (`c_banthh01` → mod-1,
`i_belt_holoadv` → mod-2) and all twelve sampled per-module loading screens
resolve and decode. The textures are found; they are not drawn. Most likely a
texture-upload path WebGL 2 treats differently — a real investigation, not a
one-line fix.

**Lesson for the gate, now acted on.** `renderer-context-is-webgl2` was written
during this change to catch a *silent fallback*, and it did its job, but it
asserted the wrong invariant — it would now fail on a correct build. It is
`renderer-context-matches-request`: the request and the result must agree,
whichever version is asked for. The deeper gap is that nothing in the suite
looks at a rendered frame; `probe-greenscreen.js` is the start of that and is
what actually caught this.

### B7 — Animated-light uniforms are re-uploaded every frame, defeating a cache the code already implements — FIXED 2026-08-30

**Found while doing the LightManager minor, fixed as its own change.**

`updateDynamicLights` starts with `this.animatedLights = []`. The rebuild loop
further down is written to *reuse* that array: it compares each light against
the entry already at its index, skips it when nothing changed, and only bumps
`animatedLightsCacheID` when something did. `ModuleArea.updateRoomAnimatedLights`
then skips any material whose `animatedLightCacheID` already matches.

The reallocation at the top makes that comparison impossible. Every entry is
`undefined`, so every light counts as changed, so the cache ID increments every
frame, so every non-lightmapped material in every visible room re-uploads its
uniforms **and gets `material.needsUpdate = true`** — which makes three
re-resolve the shader program for that material. Every frame. The optimisation
is fully written and fully inert.

Removing that one line is not the whole fix, because it is currently masking
two real bugs underneath:

1. **The unchanged branch does not advance the index.** When a light matches,
   the loop `continue`s without incrementing `animatedLightIndex`, so the next
   changed light overwrites the unchanged one's slot and the final
   `length = animatedLightIndex` truncation drops lights. Dead today because
   the branch is unreachable; live the moment the array persists.
2. **`position` is stored by reference**, not copied — `position:
   lightNode.position`. So the cached entry and the candidate are the same
   `Vector3`, and `currentAnimatedLight.position.equals(...)` compares an
   object with itself. A light that *moves* would compare equal forever and
   never update its uniform.

So the fix is three coupled changes: snapshot the position, advance the index
on both branches, then drop the reallocation.

**All three landed**, plus a fourth the others exposed: the slot comparison is
*positional*, so a reordered pool could match a light against the previous
occupant of its index. `animatedLightUUIDs` tracks identity alongside.

The block moved into its own `syncAnimatedLights()` — `updateDynamicLights` was
long enough that the animated-light tail read as an appendix, and extracting it
is also what made it testable without standing up a renderer.

Entries are now mutated in place rather than rebuilt, so the array identity is
stable: `ModuleArea` assigns that array *itself* as the uniform value, and
replacing it each frame would leave every material pointing at a dead one.
A per-frame `THREE.Color` allocation per animated light went with it.

`clearLights()` now empties the array and bumps the cache ID, which the
per-frame reallocation used to make unnecessary — without it an area change
could leave a material trusting a stale match.

**On the tests.** A regression guard that passes against the broken code is
worth nothing, so each sub-fix was reverted individually to check its test
actually bites:

| Sub-fix reverted | Tests that failed |
|---|---|
| The reallocation | 2 |
| Index advancing on the unchanged branch | 3 |
| Position stored by value | 1 |

Still unverified on a device. Booked as H14 — animated lighting is exactly the
kind of thing that fails by quietly not responding rather than by crashing.

## C. Completeness

### C1 — `strictNullChecks: false` — DONE 2026-08-30 for `src/loaders` and `src/vr`

`tsconfig.json`. The newer loader and VR code is written in a
`?? undefined` / optional-property style that only makes sense under strict
null checking, and none of it is actually checked. A4 is one instance that
happened to be visible by eye; the layered-override code is exactly the kind
of `undefined`-threading logic this would protect.

The engine as a whole cannot be flipped in one step. What is tractable: a
second config covering only `src/vr/**` and `src/loaders/**` with
`strictNullChecks: true`, added to the gate alongside the existing one, then
extended directory by directory. New code then cannot regress.

**Done as described.** `tsconfig.strict.json` plus `npm run check:strict-null`.

The scale, measured: **2339** strict-null errors across everything the two
directories transitively reach, of which **68** are inside the directories
themselves. The rest sit in `src/module` (900), `src/managers` (284),
`src/controls` (214) and elsewhere — untouched, and the gate ignores them by
path. `HARDENED` in the gate script is the list that grows; adding a directory
there and to the config's `include` is the whole ceremony.

All 68 fixed. Almost all were signatures that lied — `Promise<Uint8Array>` on
a function with `return undefined` in it. Three were more than that:

- **`ResourceLoader.getCache`** looked up `.get(resId)` twice per scope, once
  for `.has()` and once for the value, on the belief the first proved the
  second. Now one lookup per scope, in a loop over the three.
- **`InitGlobalCache` / `InitModuleCache`** called `scope.get(resType).set(...)`
  where `.get` returns `undefined` for any resource type `InitCache` did not
  seed — a throw on undefined, surfacing from whichever loader touched that
  type first. Now goes through a `cacheScopeFor` helper that creates on demand.
- **`TPCLoader.findTPC`** called `.getResourceInfo` on
  `ERFManager.ERFs.get('swpc_tex_gui')` without checking it exists. On an
  install missing a texture pack that is a throw on undefined, which reads as
  a texture bug rather than a missing file. Now an explicit error naming the
  pack.

One type outside the hardened directories changed:
`OdysseyTextureResolver` in `src/three` promised `Promise<OdysseyTexture>`
while both of its call sites already guarded with `if(!!envmap)` /
`if(!!bumpMap)`. The resolver was always allowed to return nothing; only the
type disagreed.

**The gate was verified to fail**, not merely to pass: a deliberate
`value.length` on a `string | undefined` inside `src/vr` exits 1 and names the
line; removing it exits 0.

### C2 — The module inventory is 1 of 82

`tools/vr-emulator/evidence/module-sweep-summary.json` reports
`installModuleCount: 82`, `modulesSwept: 1`. The tool built in d47994e5
specifically to make full-campaign scope tractable has been run against
`101PER` and nothing else — and that one module already reported 36 console
errors during load and render (first: `Resource not found: ResRef: t_door01`).

This is the largest completeness gap in the project, and it is not a coding
task. It is running what already exists. Everything else in this document is
an educated guess about which defects matter until the sweep says which
modules are blocked and why.

### C3 — Mod layers exist only in the browser backend

`GameFileSystem.readdirWithMetadata` returns a hard-coded `retail` layer for
every entry on the non-HTTP (Electron) path. Defensible — VR runs in the
browser — but it means the mod-layer feature cannot be exercised in the
Electron workflow used for engine work, and a texture or model upgrade that
looks broken in Electron may be fine. Worth a line in the README so it is not
rediscovered as a bug.

## D. Conciseness

- ~~**`UpdateIngame` / `UpdateDialog` / `UpdateMinigame` / `UpdateFreeLook`**
  each repeat the same eight-line world-tick tail, and three of them repeat
  the same eight-line pause-overlay block verbatim.~~ **Done 2026-08-29.**
  Extracted `updateWorldSystems(delta, lightTarget)`, `syncPauseOverlay()` and
  `updateCurrentCameraPosition()`; ~60 lines to ~15, and A2 became one
  deletion instead of four.

  `lightTarget` is a parameter because the four modes genuinely differ:
  dialogue measures light distance from the camera, since the authored shot
  rather than the party decides what is near. That was the only real variation
  in the block.

  `updateCurrentCameraPosition` stayed a separate call rather than folding
  into `updateWorldSystems`, because `UpdateMinigame` and `UpdateFreeLook`
  sequence it before `updateTime`/`FadeOverlayManager.Update` while the other
  two sequence it after. Folding it in would have silently reordered two
  modes; deduplicating it without moving it does not.
- **`VRSpike.ts` is 3142 lines and 196 static members** — the VR equivalent of
  `GameState`. The `src/vr/runtime/` hosts are well factored; VRSpike never
  got the same treatment, and every VR change pays a tax on it. First cut:
  move the render composition (`renderKeyboard`, `renderPanel`,
  `renderInGameOverlay`, `renderWorldActionPrompt`, `renderWorldTargetLabel`
  and their host fields) into a `VRFrameComposer`.
- `OverrideTextureCandidate extends OverrideResourceEntry {}` — an empty alias
  interface. Use the base type.
- `getOverrideResourcePath` re-validates arguments that
  `getOverrideResourceEntry` validates one line later.
- `handleOverlayDirectoryListing` calls `fs.statSync` on every entry although
  `readdirSync({ withFileTypes: true })` already answered `isDirectory()`, and
  `fs.realpathSync` on every entry as well. On a full retail `Override` merged
  with a mod layer that is two extra syscalls per file, on a synchronous
  request handler, on the startup path.
